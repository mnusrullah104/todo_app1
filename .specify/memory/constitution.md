# Todo App Constitution — Five-Phase Evolution

**Title**: Constitution — Evolution of Todo App (Phase I–V)
**Project Model**: Spec-Driven Development (SDD) using Claude Code + Spec-Kit Plus

## Authority + Enforcement

This Constitution governs all development across all phases. ALL code MUST be:
- Generated by Claude Code ONLY (no manual coding)
- Derived from validated specs + tasks
- Refined until correctness is agent-approved

## System Principles

### 1. Single Source of Truth

Specs define all requirements. Every implementation decision MUST trace back to a specification artifact. No feature may be implemented without corresponding spec documentation.

**Rationale**: Establishes deterministic, auditable development process where business intent is separated from technical execution.

### 2. Deterministic Execution

Claude executes approved tasks only. No implementation work may begin without:
- Validated specification in `specs/` hierarchy
- Approved plan document outlining technical approach
- Decomposed tasks with clear acceptance criteria

**Rationale**: Prevents scope creep, ensures traceability, and maintains alignment with specification-driven methodology.

### 3. Observable Progress

Every change MUST be traceable to a spec revision. All major interactions MUST be documented via:
- Prompt History Records (PHRs) for AI sessions
- Architecture Decision Records (ADRs) for significant decisions
- Version-controlled spec history

**Rationale**: Provides complete audit trail for academic evaluation and enables understanding of decision evolution.

### 4. Progressive Enhancement

Each phase builds incrementally on the previous phase. No phase may be skipped. Each phase MUST be:
- Fully functional and deployable on its own
- Testable against its specific success criteria
- Documented with complete specifications

**Rationale**: Demonstrates iterative software evolution and ensures each milestone delivers working software.

### 5. AI-Native Architecture

Chatbot + Agents become first-class interfaces. From Phase III onward, natural language interaction is the primary user interface, with traditional UIs serving as secondary access patterns.

**Rationale**: Aligns with modern AI-assisted development patterns and demonstrates practical application of conversational AI in task management.

## Five-Phase Evolution Roadmap

### Phase I — Console Todo MVP

**Objective**: Build in-memory Todo CLI with 5 Basic CRUD behaviors

**Requirements**:
- Python 3.13+
- Tasks: Create / Read / Update / Delete / Mark Complete
- Data stored in runtime memory only
- UV package manager exclusively
- Standard library preferred; minimize third-party dependencies

**Project Structure**:
```
/phase1/
├── src/
│   ├── models/            # Task data structures
│   ├── services/          # Business logic (CRUD operations)
│   └── cli/               # Command-line interface
├── specs/                 # Phase I specifications
├── specs_history/         # Version-controlled spec iterations
├── history/
│   ├── prompts/          # Prompt History Records
│   └── adr/              # Architecture Decision Records
├── README.md
├── CLAUDE.md
└── pyproject.toml
```

**Evidence of Done**:
- Working CLI demo output
- Code generation logs via Claude
- All 5 CRUD operations functional via CLI
- PHRs documenting development process
- At least 1 ADR for significant decisions

**Success Criteria**:
- Task IDs remain consistent across operations
- State management validated (add → view → update → delete → view)
- Error handling for invalid input and edge cases
- Clean module separation (models, services, CLI)
- No security vulnerabilities (input validation, no command injection)

## Cross-Phase Rules

### Spec Rules

- ✔ Update Specs BEFORE implementation
- ✔ All features under `/specs/features/*`
- ✔ Database schemas under `/specs/database/*`
- ✔ API contracts under `/specs/api/*`
- ✔ UI specifications under `/specs/ui/*`
- ✔ Architecture / overview always traceable
- ✔ Each phase maintains its own spec hierarchy

### Testing Rules

- Test evidence required per acceptance criteria
- Each phase defines appropriate testing strategy:
  - Phase I: Manual CLI testing with documented test cases
  - Phase II: API integration tests + UI E2E tests
  - Phase III: Conversational flow tests + intent recognition validation
  - Phase IV: Infrastructure tests (health checks, resource limits)
  - Phase V: Production readiness tests (load, failover, security scans)
- Chat commands tested with real user data
- No hardcoded test data in production configurations

### Versioning Rules

- All phases MUST keep feature history in `specs_history/`
- Each phase delivery MUST be deployable independently
- Semantic versioning for all specifications and constitution
- Database migrations version-controlled and reversible (Phase II+)
- API versioning strategy documented (Phase II+)
- Container image tags follow semantic versioning (Phase IV+)

### Documentation Rules

- Each phase MUST have comprehensive README with setup instructions
- Architecture diagrams required for Phase II+
- API documentation (OpenAPI/Swagger) for Phase II+
- Runbooks for operational procedures (Phase V)
- All ADRs linked from relevant specs
- PHRs organized by phase and feature under `history/prompts/`

## Phase-Specific Technology Constraints

### Phase I Constraints

**MUST use**:
- Python 3.13+
- UV package manager exclusively
- In-memory storage only

**MUST avoid**:
- Databases or file persistence
- Web frameworks
- External services or APIs
- Over-engineering for future phases

### Phase II+ Constraints

**MUST use specified stack**:
- Phase II: Next.js, FastAPI, SQLModel, Neon PostgreSQL, Better Auth
- Phase III: OpenAI ChatKit, Agents SDK, MCP
- Phase IV: Minikube, Docker, Kubernetes, Helm
- Phase V: DOKS, managed PostgreSQL, GitHub Actions (or equivalent CI/CD)

**MUST NOT**:
- Substitute core technologies without constitution amendment
- Use deprecated authentication methods (session cookies for API)
- Deploy without TLS in production (Phase V)
- Hardcode credentials or API keys

## Forbidden Practices

🚫 **Manually writing final-state code** — All code MUST be Claude-generated
🚫 **Skipping phases** — Each phase MUST be completed before next
🚫 **Hard-coding database/user data** — Use environment variables and configuration files
🚫 **Committing secrets** — Use `.env` files (gitignored) and secrets management
🚫 **Deployment without specs** — No infrastructure changes without spec approval
🚫 **Breaking backward compatibility** — Maintain API contracts across phases
🚫 **Ignoring security** — Input validation, authentication, authorization are NON-NEGOTIABLE

## Governance

### Amendment Procedure

1. Propose change with rationale in new PHR (stage: constitution)
2. Document impact on existing templates, specs, or code
3. Update constitution version according to semver rules:
   - **MAJOR**: Backward-incompatible principle removal/redefinition, phase removal/reordering
   - **MINOR**: New principle added, phase added, section expanded
   - **PATCH**: Clarifications, wording, typo fixes
4. Update all dependent templates in `.specify/templates/`
5. Create ADR if architectural implications exist
6. Commit with message: `docs: amend constitution to vX.Y.Z (brief reason)`

### Version Bump Rules

- Removal or redefinition of a principle: MAJOR bump
- Removal or reordering of phases: MAJOR bump
- Addition of a principle or phase: MINOR bump
- Expansion of existing section: MINOR bump
- Clarification without semantic change: PATCH bump
- Multiple changes: Use highest applicable bump level

### Compliance Verification

All PRs and commits MUST self-verify against this constitution. Non-compliance requires either:
- Justification in Complexity Tracking section of plan.md, or
- Constitution amendment following procedure above

**Enforcement**: This constitution supersedes all other guidance. In case of conflict between constitution and other documentation, constitution takes precedence.
