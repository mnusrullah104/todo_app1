## Key Technical Decisions

### 1. Shared Secret Pattern
**Decision**: Use BETTER_AUTH_SECRET environment variable in both frontend and backend

**Rationale**:
- Ensures JWT tokens generated by backend can be validated by both services
- Documented clearly in both .env.example files
- Follows Better Auth convention

### 2. Simplified Password Storage
**Decision**: Store passwords in dictionary for Phase II

**Rationale**:
- Phase II is a demo/prototype
- Proper solution (database column) would be added in production
- Allows focus on JWT authentication flow
- Clearly documented as simplified approach

### 3. localStorage for Token Storage
**Decision**: Use localStorage instead of httpOnly cookies

**Rationale**:
- Simpler implementation for Phase II
- Next.js App Router client components work naturally with localStorage
- Trade-off documented (production should use httpOnly cookies)
- Acceptable for demo with JWT expiration protection

### 4. Client-Side Route Protection
**Decision**: Use useEffect to check authentication in dashboard

**Rationale**:
- Next.js App Router pattern for client components
- Server-side protection would require middleware (out of Phase II scope)
- Sufficient for demo with proper API-level protection

### 5. 7-Day Token Expiration
**Decision**: JWT tokens expire after 7 days

**Rationale**:
- Balances security (not too long) with UX (not too short)
- Matches Better Auth default configuration
- No refresh token needed for Phase II scope

### 6. Generic Login Error Messages
**Decision**: Return "Invalid email or password" for both cases

**Rationale**:
- Prevents email enumeration attacks
- Security best practice
- Maintains user privacy
