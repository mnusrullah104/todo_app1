## 1. Frontend Testing Framework

### Decision
Use **Vitest** for unit/component testing and **Playwright** for E2E testing.

### Rationale
- **Vitest** is officially recommended by Next.js for App Router projects as of 2025
- Vitest provides blazing-fast, performant, dev-first experience compared to Jest
- Vitest works seamlessly with React Testing Library for component testing
- **Playwright** is the official Next.js recommendation for E2E testing
- Playwright supports multi-browser testing (Chrome, Firefox, Safari/WebKit)
- Playwright can accurately test App Router features like dynamic routing, Server Actions, and layouts

### Alternatives Considered
- **Jest**: Previously the standard, but Vitest has become preferred for Next.js App Router
- **Cypress**: Popular for E2E testing, but Playwright has better multi-browser support and official Next.js integration
- **Testing Library alone**: Insufficient for E2E scenarios requiring full browser automation

### Implementation Approach
- **Unit/Component Tests**: Vitest + React Testing Library for TaskList, TaskForm, TaskItem, AuthForm components
- **Integration Tests**: Vitest for testing API client with mocked fetch responses
- **E2E Tests**: Playwright for full user flows (register → login → create task → complete task → delete task)
- **Note**: Async Server Components require E2E tests (Vitest doesn't support them yet)

## 2. API Contract Testing

### Decision
Use **OpenAPI specification** (auto-generated by FastAPI) with **Schemathesis** for contract testing.

### Rationale
- FastAPI automatically generates OpenAPI 3.0 specifications without additional effort
- OpenAPI specs serve as executable contracts that validate requests/responses
- **Schemathesis** provides property-based testing that generates edge-case requests from specs
- Contract-first approach catches breaking changes before shipping
- OpenAPI enables automated validation middleware using `openapi-core`
- Built-in Swagger UI provides interactive API documentation

### Alternatives Considered
- **Dredd**: Good for contract testing but less Python-native than Schemathesis
- **Pact**: Consumer-driven contracts require more setup; not needed for monorepo
- **Prism**: Useful for mocking but Schemathesis offers more comprehensive testing
- **Manual testing**: Error-prone and doesn't scale with API growth

### Implementation Approach
- FastAPI automatically exposes OpenAPI spec at `/openapi.json`
- Use Schemathesis during testing phase to generate property-based tests
- Optionally use `openapi-core` for runtime request/response validation in development
- Frontend TypeScript types can be generated from OpenAPI spec for type safety
- Include OpenAPI spec in `/docs/api.md` or `/contracts/openapi.json`

### Sources

- [Enforcing API Correctness: Automated Contract Testing with OpenAPI and Dredd](https://dev.to/r3d_cr0wn/enforcing-api-correctness-automated-contract-testing-with-openapi-and-dredd-2212)

## 3. JWT Validation Performance

### Decision
Target **<50ms p95 latency** for JWT validation overhead. Use **PyJWT** with dependency injection pattern.

### Rationale
- JWT validation is stateless and lightweight when properly implemented
- PyJWT is officially recommended by FastAPI as of 2025 (over python-jose)
- Industry standard: JWT validation should add <50ms overhead to API requests
- FastAPI dependency injection enables clean, testable validation middleware
- PyJWT with `cryptography` library supports all modern signature algorithms (RS256, HS256)
- Stateless design means no database lookups for session validation

### Alternatives Considered
- **python-jose**: Previously common, but PyJWT now preferred in official FastAPI docs
- **authlib**: More comprehensive but heavier than needed for basic JWT validation
- **Manual validation**: Error-prone and reinvents the wheel

### Implementation Approach
- Install `pyjwt[crypto]` for cryptography support
- Use FastAPI `Depends()` with `HTTPBearer` security scheme
- Create `get_current_user` dependency that:
  1. Extracts token from `Authorization: Bearer <token>` header
  2. Validates signature using BETTER_AUTH_SECRET
  3. Verifies expiration timestamp
  4. Extracts user_id from token claims
- Apply dependency to all protected routes: `current_user: User = Depends(get_current_user)`
- No caching needed for tokens (validation is already fast)
- Consider refresh tokens for production (not in Phase II scope)

### Performance Targets
- **P50**: <10ms JWT validation overhead
- **P95**: <50ms JWT validation overhead
- **P99**: <100ms JWT validation overhead

## 4. Better Auth JWT Integration

### Decision
Use **Better Auth JWT plugin** with custom BETTER_AUTH_SECRET and 7-day expiration. Extract JWT via `authClient.token()` for API calls.

### Rationale
- Better Auth supports custom JWT secret via `secret` option or `BETTER_AUTH_SECRET` env var
- Better Auth JWT plugin provides server-side and client-side JWT generation
- Token expiration configurable via `expirationTime` option (default 15min, configurable to 7 days)
- Client plugin `jwtClient()` provides `authClient.token()` method to retrieve JWT
- JWT includes standard claims: `sub` (user ID), `exp` (expiration), `iss` (issuer), `aud` (audience)
- JWT can be extracted from `set-auth-jwt` response header or via dedicated endpoint
- Tokens are signed with same secret used by backend for validation

### Alternatives Considered
- **NextAuth.js**: More complex, Better Auth is more flexible for JWT-only auth
- **Custom JWT implementation**: Reinventing the wheel, Better Auth provides battle-tested solution
- **Auth0/Clerk**: Third-party services add complexity and cost for this use case

### Implementation Approach

**Backend Configuration:**
```typescript
import { betterAuth } from "better-auth";
import { jwt } from "better-auth/plugins";

export const auth = betterAuth({
  secret: process.env.BETTER_AUTH_SECRET, // Must match backend secret
  plugins: [
    jwt({
      jwt: {
        expirationTime: "7d", // 7 day expiration
        issuer: process.env.NEXT_PUBLIC_BASE_URL,
        audience: process.env.NEXT_PUBLIC_BASE_URL,
      }
    })
  ]
});
```

**Client Configuration:**
```typescript
import { createAuthClient } from "better-auth/client";
import { jwtClient } from "better-auth/client/plugins";

export const authClient = createAuthClient({
  baseURL: process.env.NEXT_PUBLIC_BASE_URL,
  plugins: [jwtClient()]
});
```

**Retrieving JWT for API Calls:**
```typescript
const { data, error } = await authClient.token();
if (data) {
  const jwtToken = data.token;
  // Attach to API requests
  await fetch(`${API_BASE_URL}/api/${userId}/tasks`, {
    headers: { "Authorization": `Bearer ${jwtToken}` }
  });
}
```

### Token Structure
- **sub** (subject): User ID
- **exp** (expiration): Unix timestamp (7 days from issue)
- **iss** (issuer): Application base URL
- **aud** (audience): Application base URL
- **Signature**: HMAC-SHA256 signed with BETTER_AUTH_SECRET

### Integration with FastAPI
1. Frontend uses Better Auth for registration/login
2. Better Auth generates JWT signed with BETTER_AUTH_SECRET
3. Frontend calls `authClient.token()` to get JWT
4. Frontend attaches JWT to all API requests: `Authorization: Bearer <token>`
5. Backend validates JWT signature using same BETTER_AUTH_SECRET
6. Backend extracts `sub` claim as user_id and verifies it matches URL parameter
